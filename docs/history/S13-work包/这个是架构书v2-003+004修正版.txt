## 第 2 章 架构不变量

### 2.1 继承 V1 的不变量（唯一编号基线）

| 编号 | 名称 | 内容 |
|------|------|------|
| **I1** | 默认不关机 | 任何状态不明确时默认不关机，不执行电源操作 |
| **I2** | 唯一电源出口 | ShutdownWorkflow 是唯一调用 IPowerService 的模块 |
| **I3** | UI 不拥有任务引擎 | UI 不拥有任务引擎、状态持久化、调度循环 |
| **I4** | Cancelled 终态 / StageToken | 取消后不可撤销；StageToken 保证单实例单次执行 |
| **I5** | HasExecuted | 标记后不可逆，永不重复执行同一任务实例 |
| **I6** | 崩溃恢复 Interrupted | 崩溃后恢复时，未完成任务标记为 Interrupted，永不补执行 |
| **I7** | 配置损坏 Faulted | 配置损坏时任务标记 Faulted，不影响其他任务 |
| **I8** | 双闸门 | 真实电源操作需双闸门（配置 + 人工确认）；无人值守/远程见 2.3 |
| **I9** | Mutex + Pipe | 单实例：Mutex 防多进程，Pipe 传递命令行参数 |

## 3.2 生命周期总流程

```
程序启动
  │
  ├── 崩溃恢复检查（I6）
  │     └── 扫描所有待恢复任务 → 标记 Interrupted
  │
  ├── 加载配置（config.json + tasks.json）
  ├── 注册所有任务（SchedulerEngine）
  │
  ▼
调度循环（等待排程触发）
  │
  ├── 单任务触发 → Countdown → 确认 → Pre-Pipeline → PowerAction
  │
  ├── 多任务同时触发 → 仲裁 → 胜出执行 / 落选改期
  │
  └── 空闲触发 → 空闲检测 → Countdown → 确认 → Pre-Pipeline → PowerAction
```

## 3.3 流程次序（统一声明）

```
Trigger → Countdown → Confirm（或无人值守等效确认）
  → Pre-Pipeline → PowerAction
```

**重要**：Pre-Pipeline 在用户确认之后执行，确保用户取消关机前不产生不可逆副作用。

# 第 6 章 步骤详述

## S13 多任务架构

### 1. 目标与验收标准

1. **状态机**：每任务实例有完备状态机（8 态），含合法转换白名单表，非法转换拒绝并记日志。
2. **崩溃恢复**：程序启动时检测上次崩溃遗留的未完成实例，标记为 `interrupted`，永不补执行关机。
3. **同时到期仲裁**：多任务同时到期时，按优先级仲裁，落选任务改期。
4. **重复任务重排**：已执行任务自动进入下一轮排程，刷新 StageToken。
5. **多任务启停**：用户可单独启用/禁用每个任务。

### 5. 关键设计——状态机

**状态集**（8 态）：

```
enum TaskInstanceState {
    waiting,       // 初始态，等待排程触发
    running,       // 正在执行（Pre-Pipeline 中）
    confirming,    // 等待用户确认（Countdown 中）
    executing,     // 正在执行电源操作
    executed,      // 已完成（终态，可重排）
    cancelled,     // 被取消（终态）
    faulted,       // 故障（终态）
    interrupted    // 崩溃恢复（终态，永不补执行）
}
```

**V1↔V2 状态名映射表**（见第 4.4 节）

**合法转换白名单表**：

| 当前态 | 合法转换 | 触发条件 | 处理动作 |
|--------|---------|---------|---------|
| waiting | → running | 排程触发 | 进入 Pre-Pipeline |
| waiting | → cancelled | 用户取消未触发任务 | 直接终态 |
| waiting | → faulted | 配置损坏检测 | 终态 |
| running | → confirming | Pre-Pipeline 完成，进入 Countdown | 打开确认窗口 |
| running | → cancelled | Pre-Pipeline 失败且 failurePolicy=block | 阻断关机 |
| running | → interrupted | 崩溃 | 恢复时标记 |
| running | → faulted | 运行时配置损坏 | 终态 |
| confirming | → executing | 用户确认 / 无人值守触发 | 执行电源操作 |
| confirming | → cancelled | 用户取消 / 倒计时超时且无人值守关 | 终态 |
| confirming | → interrupted | 崩溃 | 恢复时标记 |
| confirming | → faulted | 确认阶段配置损坏 | 终态 |
| executing | → executed | 电源操作完成 | 终态 |
| executing | → interrupted | 崩溃 | 恢复时标记 |
| executing | → faulted | 执行阶段异常 | 终态 |
| executed | → waiting | 重复任务下一轮排程 | 刷新 StageToken |
| cancelled | — | 终态，不可转换 | 任何转换拒绝并记日志 |
| interrupted | — | 终态，不可转换 | 任何转换拒绝并记日志 |
| faulted | — | 终态，不可转换 | 任何转换拒绝并记日志 |

**非法转换处理**：任何不在此表中的转换均为非法转换，拒绝并记录审计日志（级别 Error），包含当前状态、目标状态、调用来源、时间戳。

**崩溃恢复流程**：
```
程序启动时：
  1. 加载 runtime.json
  2. 对每个 status=waiting/running/confirming/executing 的实例：
     a. 标记为 interrupted
     b. 审计日志 Warning："任务 {taskId} 因崩溃恢复被标记为 interrupted，已跳过执行"
     c. UI 通知："有 {n} 个任务因上次崩溃已跳过执行"
  3. 对 cancelled/executed/faulted/interrupted 实例：保持终态
  4. 重新计算所有已启用任务的排程
```

**同时到期仲裁规则**：
```
多任务同时到期（同一秒）：
  1. 同动作合并：若多个任务均为"关机"，合并为一次电源操作
  2. 不同动作仲裁：按强度排序 关机 > 休眠 > 睡眠 > 注销
     - 高强度胜出，执行该动作
     - 落选任务改期到下一周期（至少 5 分钟后）
     - 审计日志记录仲裁结果
  3. 强制任务冲突：用户配置"不可被仲裁覆盖" → 弹出 UI 询问
```

## S14 工作日复杂排程规则 + 指定日期任务（A5 动作——新增一次性日期）

### 1. 目标与验收标准

1. **工作日规则引擎**：支持"每周工作日"、"N 小时后"、"下个工作日 N 点"、"每月第 N 个工作日"等复杂排程。
2. **一次性日期规则**（新增）：支持指定具体日期+时间的一次性任务（`schedule.type="oneday"`），过期不追溯触发，触发后任务按一次性任务终结处理。
3. **例外日期**：用户可配置例外日期（节假日），在例外日期不触发。

### 3. 架构影响

**新增模块**：
- `INextTimeCalculator`：排程计算器接口
- `WeekdayRule`：工作日规则计算器
- `DayOfMonthRule`：每月第 N 个工作日规则
- `HolidayCalendar`：节假日日历
- `OneTimeDateRule`：一次性日期规则计算器（纯函数，输入目标日期时间，输出下个触发时间——若已过期则返回 null，任务终结）

### 4. 数据模型

```json
{
  "schedule": {
    "type": "oneday",  // 或 "weekly" / "monthly" / "workday"
    "date": "2025-12-25",
    "time": "18:00",
    "endAfter": true   // 一次性任务执行后终结
  }
}
```

**一次性日期规则说明**：
- `date` + `time` 指定精确触发时间
- 若 `date + time` 已过当前时间 → 不触发，任务标记为 `cancelled`（告知用户"已过期"）
- 触发后任务自动终结（不再重排）
- 计算器为纯函数：输入 `(taskConfig, now)` → 输出 `DateTime?`（null 表示无后续触发）

## S20 无人值守

### 4. 流程修正

```
Countdown 结束，无人确认
  ├── 无人值守 enabled → 执行 UnattendedPolicy
  │   ├── 进入 Pre-Pipeline（正常执行，仅跳过用户确认）
  │   │   └── action 按配置决定
  │   ├── forceShutdown → Pre-Pipeline 后关机
  │   ├── forceKillAndShutdown → Pre-Pipeline 中强杀 + 关机
  │   └── hibernate → Pre-Pipeline 后休眠
  └── 无人值守 disabled → 默认不关机（I1），倒计时结束，取消
```

**重要**：无人值守时仍执行 Pre-Pipeline，仅跳过用户确认环节。不跳过 Pre-Pipeline。

## S23 远程控制（A2 动作——TLS 强制条款）

### 5. 关键设计——安全机制

#### 5.6 PIN 限速与锁定（CR-002 前置①）

- 连续 5 次 PIN 输入失败 → 锁定 15 分钟
- 锁定期间拒绝所有配对请求
- 记录审计日志，解锁需通过本地 UI 操作

#### 5.7 请求鉴权（CR-002 前置②——含 TLS 强制条款）

**鉴权机制**：
- 配对后，每次请求携带 `deviceId` + `HMAC-SHA256(deviceId + timestamp + nonce, sharedSecret)`
- 不依赖来源 IP 鉴权（DHCP 漂移、局域网内 IP 可伪造）

**TLS 强制条款**（A2 动作——关键修改）：
- **远程触发 + 无人值守组合时，传输强制使用 TLS**（自签名证书或用户导入证书）
- 未启用 TLS 时，该组合被拒绝，远程触发回退到本地确认流程
- 仅读命令（`queryStatus`、`listTasks`）在未启用 TLS 时可选接受

#### 5.8 远程触发 + 无人值守组合规则（CR-002 前置③——含 TLS 行）

| 场景 | 行为 |
|------|------|
| 无人值守 disabled | 远程触发走正常 Countdown 确认流程 |
| 无人值守 enabled + 远程命令在白名单中 + **TLS 已启用** | 跳过本地确认，执行 Pre-Pipeline → PowerAction |
| 无人值守 enabled + 远程命令在白名单中 + **TLS 未启用** | **组合被拒绝**，远程触发回退本地确认流程 |
| 无人值守 enabled + 远程命令不在白名单中 | 拒绝命令 |

**安全增强措施**（同时实施，非二选一）：
1. **审计升级为高危标记**：`[REMOTE+UNATTENDED] High risk: remote {ip} triggered shutdown via unattended policy`
2. **系统托盘显著提示**：托盘图标闪烁 + 通知气泡"远程命令已触发关机（无人值守模式）"

#### 5.9 局域网威胁模型（CR-002 前置④——含 TLS 行）

```
# 7.5 局域网威胁模型

## 防御范围
- 防止局域网内未授权设备连接、执行命令
- 防止已配对设备被仿冒（deviceId + HMAC 鉴权）
- 防止中间人攻击（远程+无人值守强制 TLS）

## 防御边界
- 配对：PIN 码 + 限速 + 锁定
- 鉴权：HMAC + 时间戳 + nonce（不依赖 IP）
- 传输：远程触发+无人值守组合强制 TLS，仅读命令可选明文
- 命令：白名单 + 禁止修改配置
- 组合：远程+无人值守 → 高危标记 + 托盘提示

## 接受的风险（推迟 V3）
- 物理接入攻击者（直接操作本机或网络硬件）
- 局域网内 ARP 欺骗/DHCP 投毒（需要物理接入或网络设备控制权）
- 旁路攻击（如功耗分析、时序分析）

## 不回退场景
- 任何远程命令不能绕过本地安全策略
- 任何远程命令不能修改本地配置
- 任何远程命令不能执行白名单以外的操作
```

| 术语 | 定义 |
|------|------|
| **Pre-Pipeline** | 关机前流水线，在 Countdown 确认后、PowerAction 前执行 |

| **Countdown** | 关机倒计时，显示给用户确认或取消的时间窗口 |
| **TriggerType** | 触发类型：Time（定时）、Idle（空闲）、Remote（远程） |
| **FailurePolicy** | 失败策略：block（阻断关机）/ continue（继续执行） |
| **Magic Packet** | WoL 特殊网络包，6 字节 0xFF + MAC 地址重复 16 次 |
| **JSON-RPC 2.0** | 远程过程调用协议，基于 JSON 的轻量级通信协议 |
| **ARCH-CR** | 架构变更申请，用于修改架构不变量的正式流程 |
| **Gate 0 / Gate 1** | 步骤开始前/完成后的验证闸门 |

### 5. 关键设计——白名单

**本地命令白名单**（F5 关机前命令执行）：

- 失败策略：block（阻断关机）/ continue（继续执行，记录错误日志）

## 修正 4：S23 新增"远程命令白名单默认规则"小节（D2 第二部分）

**插入位置**：S23 §5 关键设计——安全机制，在 §5.9 之后新增 §5.10

```markdown
#### 5.10 远程命令白名单默认规则

**远程命令白名单**（F10 远程控制）与 F5 本地命令白名单完全独立，互不干扰。

**默认规则**：
- 默认仅包含只读命令：`queryStatus`、`listTasks`
- 触发类命令（`triggerShutdown`、`cancelShutdown`）需用户显式启用
- 任何未在白名单中的命令被远程调用时，拒绝执行并记录审计日志 Error

**与无人值守的交互**：
- 远程命令 `triggerShutdown` 只有在白名单中 + 无人值守已启用 + TLS 已启用时，才可跳过本地确认
- 若 `triggerShutdown` 不在白名单中，即使无人值守已启用，远程触发也被拒绝

**安全限制**：
- 远程不能修改远程命令白名单本身
- 远程不能修改本地命令白名单（S19）
- 远程不能修改本地安全策略配置
```
