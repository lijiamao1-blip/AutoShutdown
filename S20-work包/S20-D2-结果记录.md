## 返修内容

### 修复 — 空闲触发 Confirming 到期边界的 fail-closed（`SchedulerEngine.ResolveCountdownConfirmationAsync`）

原逻辑：

```csharp
if (State == Confirming && IsIdleTriggered && _idleMonitor is not null)
{
    var definition = _taskService.Get(...);
    if (definition is not null)
    {
        var idleDuration = _idleMonitor.GetIdleDuration();
        if (idleDuration is not null && !IsIdleDue(...))
        { cancel (IsIdleRecovered); }
    }
}
```

问题：`idleDuration == null`（输入状态未知）或 `_idleMonitor == null` 或 `definition == null` 时整个分支跳过，实例落入无人值守/人工确认继续执行。

新逻辑（任一条件即拒绝，返回 false 提前终结）：

1. `_idleMonitor == null` → `CancelIdleBoundaryAsync`（安全取消，不标记 IsIdleRecovered）。
2. `_taskService.Get(SourceTaskId)` 为 null（任务定义缺失）→ `CancelIdleBoundaryAsync`。
3. `GetIdleDuration() == null`（如 GetLastInputInfo 失败）→ `CancelIdleBoundaryAsync`，注释明确「输入状态未知，不进入 Confirming→Running、不调用 Handler/Pipeline/电源」。
4. `!IdleShutdownRule.IsIdleDue(...)`（输入已恢复）→ 沿用既有 `CancelIdleTriggeredAsync`（设置 `IsIdleRecovered=true`，审计语义不变）。

新增 `CancelIdleBoundaryAsync`：按冻结白名单 `Confirming→Cancelled` 终结并持久化，与输入恢复取消区分，不标记 `IsIdleRecovered`。全部拒绝路径返回 false，`EnterExecutingAsync` 提前返回，因此 Handler/Pipeline/电源调用均为 0。

## 关键安全不变量核对

- **输入状态不明即 disabled/fail-closed**：空闲触发任务在 Confirming 到期边界，`idleMonitor==null`、定义缺失、`GetIdleDuration()==null`、输入恢复四者任一即拒绝并安全取消（S20-D2 核心）。
- **拒绝后不执行**：全部拒绝路径返回 false，`EnterExecutingAsync` 提前返回——不进入 `Confirming→Running`、不调用 Handler、不运行 Pre-Pipeline、不调用电源（测试断言 Pipeline=0、电源=0）。
- **输入未知不误记为「已恢复输入」**：`CancelIdleBoundaryAsync` 不设置 `IsIdleRecovered`；仅真实输入恢复才经 `CancelIdleTriggeredAsync` 设置 `IsIdleRecovered=true`（审计语义准确区分，测试 1/2/3 断言 false、测试 4 断言 true）。
- **既有路径回归**：输入恢复胜出与「仍空闲 + 有效无人值守仅一次执行」均通过（测试 4/5）。
- **不改冻结状态机/双闸门/唯一电源出口/Pre-Pipeline 顺序**：仅新增边界 fail-closed 分支，`Confirming → Running → OfficeSave → RunCommands → CloseApps → 唯一电源调用` 链路不变。
- **无真实关机/重启/睡眠/休眠/关闭真实用户应用**：全程 Fake/Guarded PowerService + RecordingPowerService 替身；S19 限制继续有效（RunCommands 本地白名单默认空，D2B/D2C 未处理）。
